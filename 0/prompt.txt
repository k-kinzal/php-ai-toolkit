## 2. Setup-skill instruction structure (the house style)

Every `SKILL.md` follows the same sections, in this order:

1. Frontmatter `name` + long `description` stuffed with trigger phrases.
2. **Prerequisites** — inspect `composer.json` (autoload roots, existing config, existing scripts, PHP floor) before writing anything; `composer require --dev k-kinzal/php-ai-toolkit`.
3. **Template** — "Read the template from `vendor/k-kinzal/php-ai-toolkit/skills/&lt;skill&gt;/&lt;file&gt;` and apply it to the project root as `&lt;file&gt;`." Templates are literal files in the skill dir, never inlined.
4. **Merging with existing configuration** — explicit per-key merge rules; recurring rule "do not add broad excludes/ignores just to make it pass; fix the source or report what needs a human decision."
5. **Recommended Composer Scripts** — canonical names: `test` / `test:unit` / `test:unit:legacy`, `lint` (aggregate), `phpstan`, `compat`, `loc-guard`, `deptrac`, `format`, `format:check`. Aggregate order in root `composer.json`: `@format:check → @phpstan → @compat → @loc-guard → @deptrac`. Skills instruct merging into an existing `lint`/`check` rather than replacing.
6. **Verification** — exact command + exit-code semantics.
7. **References** — links to `vendor/k-kinzal/php-ai-toolkit/docs/&lt;tool&gt;.md`.

Each tool also gets a matching doc under `docs/` (`docs/loc-guard.md`, `docs/deptrac.md`, …) linked from `README.md` and `AGENTS.md`.

CI convention (`skills/setup-toolkit-github-actions/{SKILL.md,ci.yml}`): two jobs, `tests` and `lint`, both matrixed over PHP 8.0–8.5, each PHP minor copying `composer.lock.php-&lt;ver&gt;` into `composer.lock`; every gate is its own named step (`composer loc-guard`, `composer deptrac`, …) — the skill explicitly forbids hiding gates behind one `composer lint` step, and requires SHA-pinned actions, `permissions: contents: read`, `concurrency`, `fail-fast: false`, `timeout-minutes`.

Distribution detail worth knowing: `/Users/ab/Projects/php-ai-toolkit/.gitattributes` `export-ignore`s `docs/` and `tests/` but **not** `skills/`, so skills ship in the dist tarball (skill "References" links into `vendor/.../docs/` which is not actually exported — a pre-existing inconsistency). Skills are auto-discovered by directory scan at install time (`src/Installer/Cli/Command/PackageSkillDirectoryScanner.php` — `scandir` over `skills/`, every subdirectory becomes an installable skill), so **adding a new `skills/setup-toolkit-&lt;x&gt;/` directory requires zero registration code**.

The closest existing precedent is `SrcUnitTestPairRule` — a PHPStan rule that *does* touch the filesystem: it implements `Rule&lt;FileNode&gt;` and inspects `$scope-&gt;getFile()`, mapping `src/…Foo.php` ↔ `tests/Unit/…FooTest.php` via configurable `srcMarker` / `unitTestMarker` / `srcUnitTestPairExcludePatterns` (`src/PhpStan/Rule/SrcUnitTestPairRule.php`, registered in `extension.neon` under `parameters.customRules`). So a "required file must exist" check is provably expressible as a PHPStan rule — but only per-analysed-PHP-file. Counting files per directory, counting subdirectories, or flagging non-PHP files has no PHPStan entry point (PHPStan only visits files it analyses, and directories with zero PHP files are invisible).

## 4. Sibling repo on disk: `/Users/ab/Projects/guard-rs` — the actual "LocGuard family"

This is the reference architecture you're looking for. It is a **Rust** repo by the same author (`repository = "https://github.com/k-kinzal/guard-rs"`) containing three independently published crates, intentionally **not** a Cargo workspace and sharing no code:

- `/Users/ab/Projects/guard-rs/locguard/` — size/length limits (the Rust analogue of the PHP LocGuard).
- `/Users/ab/Projects/guard-rs/layerguard/` — directory-level layer boundaries (Rust analogue of Deptrac).
- `/Users/ab/Projects/guard-rs/cycleguard/` — Acyclic Dependencies Principle over directory components (Tarjan SCC).

`README.md` frames them as covering "the structural axes of ArchUnit-style architecture testing: **size** (locguard), **layering** (layerguard), and **cycle-freeness** (cycleguard)" — a directory/file-structure guard is the obvious fourth axis and there is currently no crate for it.

The per-guard conventions are codified in `/Users/ab/Projects/guard-rs/AGENTS.md` ("Conventions"), and any new guard is expected to match:

- Library crate `src/lib.rs` exposing `run(paths, config) -&gt; Result&lt;Report&gt;`, thin `src/main.rs` on `clap` derive.
- Config loaded via `Config::load` from `&lt;tool&gt;.toml` (`locguard.toml`, `layerguard.toml`, `cycleguard.toml`) at the crate root.
- `--format text|json`, exit code `1` on violations.
- Library exposes a typed `Error` enum in `src/error.rs`; binary wraps with `anyhow` (never return `anyhow::Error` from the library).
- `[lints]` table: `unsafe_code = "forbid"`, `clippy::all` + `clippy::pedantic`, panic-source guard (`unwrap_used`/`expect_used`/`panic`/`todo`/`unimplemented` = warn).
- Internal module layout is uniform: `src/{config,analyze,discover,report,error,syntax|imports|resolve|graph}` with the leaf data layers forbidden from depending on logic layers.

Config formats (TOML, flat `[limits]` for locguard; array-of-tables for the structural guards):

`/Users/ab/Projects/guard-rs/layerguard/layerguard.toml`
```toml
exclude = ["target"]

[[layers]]
name = "imports"
path = "src/imports"

[[rules]]
from = "imports"
deny = ["analyze", "discover", "resolve", "config", "report", "error"]
# or: allow = [...]  -&gt; non-empty allow forbids every unlisted layer
```

`/Users/ab/Projects/guard-rs/cycleguard/cycleguard.toml`
```toml
exclude = ["target"]

[[components]]
name = "imports"
path = "src/imports"
```

`locguard.toml` is a single flat `[limits]` table with ~500 keys, each metric doubled with a `_without_tests` variant (e.g. `max_file_lines` / `max_file_lines_without_tests`, `max_items_per_file`, `max_top_level_structs_per_file`, `max_module_nesting = 4`, `max_columns = 120`). Note `max_items_per_module`, `max_mods_per_file`, `max_module_nesting` — the closest existing thing to "structure" limits, but they're *syntactic* modules, not filesystem directories. locguard also has a **calibration mode** (`--stats`, `--stats-summary`, both with `--format json`) that prints the max observed value per metric so you can seed a config against an existing codebase — a very useful pattern for a structure guard whose thresholds are inherently project-specific.

Integration/CI in guard-rs (`/Users/ab/Projects/guard-rs/.github/workflows/ci.yml`): a `discover` job globs `*/Cargo.toml` to build the crate matrix, a `check` job runs fmt/clippy/test per crate, and a **`dogfood` job runs every guard against every crate that contains a matching `&lt;crate&gt;/&lt;guard&gt;.toml`** — so adding a fourth guard needs no CI change. Plus `/Users/ab/Projects/guard-rs/scripts/quality-guards.sh`, a hand-written ledger of grep-based guards for patterns the tools don't cover (e.g. TODO/FIXME debt markers).

## Bearing on your decision

Concrete constraints from the evidence, not opinions:

- The "LocGuard pattern" in the PHP world is **not** a standalone package — it is a second binary inside `k-kinzal/php-ai-toolkit` with its own top-level namespace, its own YAML config at project root, its own `ai|text|json` reporters, and its own Composer script wired into `lint` + a named CI step. Replicating it for a structure guard means: `src/StructGuard/` + `bin/struct-guard` + `struct.yaml` + `skills/setup-toolkit-struct-guard/{SKILL.md,struct.yaml}` + `docs/struct-guard.md` + a `deptrac.yaml` layer + a `composer.json` `bin`/`scripts` entry. Zero installer changes (skills are scandir-discovered).
- The "standalone tool with its own config" pattern is what `guard-rs` does, but that repo is Rust-only and Rust-parsing; a PHP/language-agnostic structure guard would not naturally live there unless you write it in Rust as a language-neutral filesystem checker (which is plausible — directory/file-count/naming rules need no parser at all).
- The PHPStan-rule route is materially constrained: PHPStan only surfaces files it analyses (`Rule&lt;FileNode&gt;`, `$scope-&gt;getFile()` — see `SrcUnitTestPairRule`), it cannot see empty or non-PHP directories, has no per-directory aggregation node, and its errors must be attributable to a file+line. "Max files per directory" / "max subdirectories" / "required file `README.md` exists" are directory-scoped facts with no owning PHP file, so they fit the CLI shape (LocGuard's `Violation` already tolerates directory-ish reporting via `path` + `line`) far better than the rule shape.</result>
