# Doctest Configuration

Doctest configuration generated by the `/setup-toolkit-doctest` skill.

## Purpose

`doctest` runs the examples written in PHPDoc blocks, the way Python's `doctest` and Rust's doc tests
run theirs. Prose in a docblock says what a symbol is for; an example says what calling it does, and
because the example is executed, it cannot quietly stop being true.

```php
/**
 * Adds two numbers.
 *
 * @example Adding two numbers
 *     (new Calculator())->add(1, 2) // => 3
 */
public function add(int $left, int $right): int
{
    return $left + $right;
}
```

```

- files: 42
- examples: 118
- passed: 117
- failed: 1
- skipped: 0
guidance:
- A failing example means the documentation and the code disagree; decide which one is wrong before editing either.
...
failures:
1. src/Calculator.php:11 [doctest]
   example: App\Calculator::add()#1
   rerun: vendor/bin/doctest --filter='App\Calculator::add()#1'
   - line 1: The statement did not produce the documented value.
     code: (new Calculator())->add(1, 2)
     expected: 3
     actual: 4
```

The grammar is the one [k-kinzal/doctest-php](https://github.com/k-kinzal/doctest-php) established, so
examples written for that extension run here unchanged. What this toolkit adds is a standalone
command, an AI-oriented report, per-example identifiers that make a single example runnable on its
own, a PHPStan rule that can require examples on public API, and a documentation site that renders
each example next to the command that runs it.

## Command

Run:

```bash
vendor/bin/doctest --config=doctest.yaml
```

Exit codes:

- `0`: every example held
- `1`: at least one example failed
- `2`: configuration or runtime error

Options:

| Option | Meaning |
|--------|---------|
| `--config PATH` | Path to `doctest.yaml` (default: `doctest.yaml`) |
| `--filter ID` | Run only examples whose identifier or file path contains `ID` |
| `--list` | Print the identifier and location of every selected example without running it |
| `--reporter NAME` | `ai`, `text`, or `json` |
| `--format NAME` | Alias of `--reporter` |

## Example Identifiers

Every example has an identifier: the symbol it documents, then `#` and its one-based position within
that symbol's docblock.

```
App\Calculator#1                 the first example on the class
App\Calculator::add()#2          the second example on the method
App\helpers()#1                  the first example on a function
```

The identifier is what makes a single example runnable on its own:

```bash
vendor/bin/doctest --list
vendor/bin/doctest --filter='App\Calculator::add()#2'
```

Matching is a case-insensitive substring of the identifier or of the file path, so `--filter=add`
runs every example of every `add()`, and `--filter=src/Calculator.php` runs the file.

The same identifier is printed next to each failure, is the name of the PHPUnit test case, and is
shown on the generated documentation page. One string addresses an example everywhere.

## Where Examples Are Written

An example is read from a docblock on a file, a class-like, a method, or a function. Two notations
are recognized, in this order:

### `@example` blocks

The tag takes an optional description, and the indented lines under it are the example:

```php
/**
 * @example Adding across several lines
 *     $calculator = new Calculator();
 *     $calculator->add(
 *         10,
 *         5
 *     ) // => 15
 */
```

The block ends at the next `@tag` line. A tag whose only content is on the tag line itself —
`@example $calculator->add($left, $right)` — documents a shape rather than a program: it is rendered
on the documentation site and reported as skipped, never executed.

### Fenced `php` blocks

````php
/**
 * ```php
 * (new Calculator())->add(5, 3) // => 8
 * ```
 */
````

Only a fence whose info string is exactly `php` is executed. A fence marked anything else — say
` ```php-ignore ` — is rendered as ordinary code and never run, which is how an illustrative snippet
that must not execute is written.

## Assertions

| Notation | Checks |
|----------|--------|
| `expr // => value` | The value of `expr` is identical (`===`) to the value of `value` |
| `stmt // Output: text` | What `stmt` printed equals `text`, ignoring one trailing newline |
| `expr // throws Class` | `expr` throws `Class`, or a subclass of it |
| `expr // throws Class: fragment` | It also throws with a message containing `fragment` |
| no marker | The line runs without raising anything |

A marker is only read from a real trailing comment. A `//` inside a string literal stays part of the
code:

```php
/**
 * @example Leaving a slash pair alone
 *     $url = "https://example.com"; // Output:
 *     echo $url; // Output: https://example.com
 */
```

The expected value of `// =>` is PHP source, evaluated in the same namespace as the example, so
`// => Suit::Hearts` and `// => ['a' => 1]` both work.

Every statement of an example runs even after one fails, so a single run reports every broken
assertion in the example rather than only the first.

## What an Example Can See

Each example runs on its own, with variables carried from one line to the next inside that example
and nothing carried between examples.

The namespace and the `use` statements of the documenting file are replayed in front of the example,
so an example spells a class the way the file around it spells it:

```php
namespace App\Billing;

use App\Money;

/**
 * @example Naming types the way the file names them
 *     $ledger = new Ledger();
 *     $ledger->balance() // => new Money(0)
 */
```

The code an example documents is made available before the example runs. A class an autoloader can
already resolve is never included by hand, so autoloaded projects are never at risk of a redeclared
class; only files that define nothing loadable — a plain function file, for instance — are read.
Point `bootstrap` at a file that has to be loaded first.

A warning, notice, or deprecation raised while an example runs fails that example. An example that
only works by emitting a diagnostic is documenting something the caller will hit too. Diagnostics
silenced with `@` are left alone.

## Running Under PHPUnit

Extend `DoctestTestCase` in the project's own test suite to have every example run as its own
PHPUnit test:

```php
namespace Tests\Unit;

use Override;
use PhpAiToolkit\PhpUnit\Doctest\DoctestTestCase;

final class DocumentedExampleTest extends DoctestTestCase
{
    #[Override]
    public static function doctestConfigPath(): string
    {
        return __DIR__ . '/../../doctest.yaml';
    }
}
```

Each example becomes one test case named `<symbol> example #<n>: <description> [<identifier>]`, so a
failing PHPUnit run names the example that broke and hands back the identifier that re-runs it alone.

The class reads its metadata from PHPUnit attributes and needs PHPUnit 10 or later. On PHPUnit 9,
extend `PhpAiToolkit\PhpUnit\Doctest\Legacy\LegacyDoctestTestCase` instead: it binds the same data
provider through a doc-comment annotation, which is how PHPUnit 9 reads metadata and how PHPUnit 12
no longer does.

Running the examples under PHPUnit and running them with `vendor/bin/doctest` are the same execution
path; use whichever the project's CI already reports through.

## Requiring Examples on Public API

[RequireExampleOnPublicApiRule](rules/RequireExampleOnPublicApiRule.md) reports a declaration that
carries `@visibility public` without a runnable example. The tag is how a project states that a
symbol is part of the surface other code is invited to use; the rule makes that statement carry an
executable demonstration. Untagged declarations are not reported, so the requirement is adopted one
boundary at a time.

## Relationship to DocGen

`doc-gen` renders the same examples it would run. Each `@example` block becomes a figure carrying a
**doctest** badge, its assertions styled by kind, a **copy** button for the example itself, and a
**run** button that copies `vendor/bin/doctest --filter='<identifier>'`. Display-only examples are
rendered without the badge. See [DocGen Configuration](doc-gen.md).

## Configuration

Example `doctest.yaml`:

```yaml
paths:
  - src

exclude:
  - 'src/Generated/*'

bootstrap: vendor/autoload.php

report:
  reporter: ai
  order_by:
    - path
    - line
```

`paths` (default `['src']`) lists the files and directories to scan, relative to the config file
directory.

`exclude` (default `[]`) is a list of fnmatch globs applied to project-relative paths. `*` crosses
`/` boundaries, so `src/Generated/*` removes a whole subtree.

`bootstrap` (default none) names a file to include once before the first example runs, relative to
the config file directory unless it starts with `/`. A project whose Composer autoloader is enough —
which is most of them — needs no bootstrap: the command loads it already.

## Reporter

`report.reporter` (default `ai`) selects the output format:

- `ai` — a structured report with per-failure remediation guidance, intended for coding agents. The
  first line is `DOCTEST_PASSED` or `DOCTEST_FAILED`, and every failure carries the command that
  re-runs that one example.
- `text` — concise human output.
- `json` — machine output for CI and other consumers.

`report.order_by` (default `['path', 'line']`) decides the order failures are printed in. Supported
fields are `path`, `line`, and `symbol`. The order is decided by doctest rather than by discovery
order, so the same sources produce the same report on every platform and PHP version.

## How to Fix a Failure

A failing example means the documentation and the code disagree. Decide which one is wrong before
editing either:

- **The example is right**: the code no longer does what callers were promised. Fix the code.
- **The code is right**: the documentation went stale. Fix the example, keeping the assertion.

Deleting an example, or dropping its marker so the line becomes a smoke test, is not a fix: it
removes the check instead of satisfying it.

## CI

`composer doctest` runs as its own job of the CI workflow on every supported PHP minor, so an
example that only holds on one version is caught. See
