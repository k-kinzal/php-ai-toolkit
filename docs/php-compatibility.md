# PHPCompatibility Configuration

PHPCompatibility configuration generated by the `/setup-toolkit-php-compatibility`
skill.

## Purpose

PHPCompatibility answers one question no other gate in this toolkit answers: is
the code actually runnable on the lowest PHP version the package claims to
support? PHPStan is told which PHP version to reason about but analyses the code
under the runtime it was started on, PHP-CS-Fixer only reformats, and a test run
proves the suite passes on the runtime that ran it. None of them notice a
`readonly` property or an `enum` slipping into a package that declares
`"php": "^8.0"` — until someone installs it on PHP 8.0 and gets a parse error.

That drift is the normal failure mode for AI-written code: the syntax an agent
reaches for is the syntax of the PHP it is thinking in, which is whatever is
current, not whatever the package promised. PHPCompatibility reports it per
feature, at the line that introduced it.

PHPCompatibility is a PHP_CodeSniffer standard rather than a standalone binary,
so it runs on `phpcs` and never rewrites code.

## Command

Run:

```bash
composer compat
```

`phpcs` auto-discovers `phpcs.xml.dist`, so the Composer script carries no
`--standard` flag. Exit codes are PHP_CodeSniffer's: `0` when nothing is
reported, non-zero when something is.

Two flags are worth knowing while fixing a report:

```bash
vendor/bin/phpcs -s                 # append sniff identifiers to each message
vendor/bin/phpcs --report=source    # summarise which features were used
```

## Configuration

```xml
<?xml version="1.0"?>
<ruleset name="php-ai-toolkit-compat">
    <file>src</file>
    <file>tests</file>

    <exclude-pattern>tests/Fixture/*</exclude-pattern>

    <config name="testVersion" value="8.0-"/>

    <rule ref="PHPCompatibility"/>
</ruleset>
```

### `testVersion="8.0-"`

Sets the floor of the supported range. The trailing `-` means "8.0 and up", so
every feature introduced after 8.0 is reported.

**Why:** `composer.json` declares `"php": "^8.0"`, and the CI `tests` and `lint`
matrices both start at PHP 8.0. The floor written here has to be the same
number, because it is the only one of the three that is checked against the
source. If the declared floor and this value ever disagree, the package is
advertising support it does not verify.

### `<file>src</file>` and `<file>tests</file>`

Gates the production sources and the test suite, not just `src/`.

**Why:** a test that uses 8.1 syntax fails to parse on PHP 8.0 just as loudly as
production code does, and the CI `tests` matrix runs the suite on the floor. The
gate is cheaper than the leg that would otherwise find it.

### `<exclude-pattern>tests/Fixture/*</exclude-pattern>`

Excludes fixtures that a test reads rather than runs.

**Why:** a fixture fed to an analyser as text is test data, not code that has to
run on the floor, and it often carries post-8.0 syntax on purpose — an enum a
rule is shown analysing, say. Excluding those files is the difference between the
gate reporting real drift and reporting the test data. Exclude nothing the
runtime actually executes.

### `<rule ref="PHPCompatibility"/>` alone

Loads the compatibility standard and nothing else.

**Why:** code style belongs to PHP-CS-Fixer, which owns the same files. Adding
PSR-12 or Squiz sniffs here would give two tools an opinion about the same
formatting, and they would fight: `composer format` would rewrite what
`composer compat` had just reported. Keeping this ruleset compatibility-only
keeps each file's formatting owned by exactly one command.

## Dependency Line

The gate depends on which PHPCompatibility line is installed, and the wrong one
passes silently:

- **9.x** tops out at PHP 7.4 feature detection. It does not know about
  `readonly`, enums, `never`, first-class callables, or `new` in initializers,
  so a codebase full of 8.1 syntax scans clean under it.
- **10.x** carries the PHP 8.0–8.5 sniffs and currently accepts
  PHP_CodeSniffer `^3.13.3 || ^4.0`. It is the only line that can gate an 8.0
  floor; this toolkit chooses PHP_CodeSniffer 4 as its own default policy.

`composer.json` therefore requires `phpcompatibility/php-compatibility:
^10.0@alpha` with `squizlabs/php_codesniffer: ^4.0`. 10.x has no stable tag yet,
so the constraint takes the tagged pre-release rather than the moving
`dev-develop` branch.

The standard is registered by `dealerdirect/phpcodesniffer-composer-installer`,
which is a Composer plugin, so it is listed under `config.allow-plugins`.
`vendor/bin/phpcs -i` should list `PHPCompatibility`.

## Bareword Version Tokens

PHPCompatibility matches version-specific tokens lexically, so a bareword
constant such as `T_ENUM` is reported wherever it textually appears — including
inside a `defined('T_ENUM')` guard that exists exactly to keep the code runnable
on the floor. Reference such constants through `constant('T_ENUM')`, where the
name is a string rather than a token, and the guard keeps working while the gate
stays quiet.

This is not a suppression: the code still never names a constant the floor does
not have. The toolkit's own `ForbiddenCommentRule` forbids silencing a report
with a comment, and a genuine violation means either the code comes down to the
floor or the declared floor goes up.

## CI

`composer compat` runs as a named step of the `lint` job, on every PHP minor in
the matrix, alongside formatting, PHPStan, LocGuard, TreeGuard, and Deptrac.
See [GitHub Actions Configuration](github-actions.md).

Running it on every minor rather than once is deliberate but cheap: `phpcs`
reads `testVersion` from the ruleset, so each leg reports the same floor
violations, and a leg that cannot even install the standard is itself the
finding.

## Relationship to PHPStan

PHPStan's `phpVersion` can also flag version drift and needs no second
toolchain, which makes it a reasonable alternative for a project that wants one
analyser. It reports newer syntax as a parse error that stops analysis of the
file, though, and its messages name the syntax rather than the feature and the
version that introduced it. The toolkit picks PHPCompatibility for the
per-feature messages and the stable sniff identifiers. Only one of the two
should be the compatibility gate; running both means two reports of the same
drift.
